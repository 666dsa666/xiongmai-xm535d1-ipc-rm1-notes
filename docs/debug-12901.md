# 12901 `/usr/bin/debug`: auth downgrade + pre-auth heap overflow

`/usr/bin/debug` is the vendor debug service on TCP **12901**. Its binary is
**byte-identical in V5.00, V5.01, V5.02, V5.04 and V5.07**
(md5 `f35fcd314982b9ce4cbb2140cf9c6cb1`, 126,180 B, ARM32 EABI), so the findings below
apply to all those builds.

> Summary: the vendor RSA signature is **not enforced** — the client can select a weak
> safety-code mode instead. That gives authenticated access to the debug protocol, but the
> post-auth command is a **fixed literal** (`timetest`), not a root shell. The serious bug
> is a **pre-auth heap overflow** in the `Update` stage (up to 225 bytes), a network-only
> RCE research target. No vendor private key is needed anywhere.

## Protocol

Five sequential stages: `Open → Update → RS → Check → Run`.

- 16-byte header + payload; the "checksum" is an obfuscated 16-bit length check
  (`XmDvr_RandNum_procString`) — **freely forgeable, not a security control**.
- `Open` (no auth): daemon creates an ephemeral 1024-bit RSA key, replies with public
  N/E and 24-byte connection seeds.
- `Update` (no auth): client uploads its own RSA public key (used for reply encryption)
  and a licence text `N=…,E=…,`; the E field is copied into a 290-byte heap buffer with a
  257-byte maximum → **up to 225 bytes of heap overflow, before any authentication**.
- `RS` (the "authentication" stage) has **two client-selectable modes** selected by the
  length of the client field:
  - **short (≤100 bytes) → VSC**: reads `/var/T8aYMi2q`, derives 10 decimal digits
    (safety code) and compares them; the safety code is **offline-computable** from
    device data (SN/date/production date, unsalted MD5);
  - **long (>100 bytes) → RSV**: genuine RSA PKCS#1 v1.5 signature verification against
    the **public** key in `TelPubBase`. The check is real, but the client is free not to
    use it.
- `Check`: compares a client value against a constant + per-connection seeds
  (client-computable).
- `Run`: `popen("timetest", "r")` — the command is a **fixed local literal**, not
  client-controlled. `timetest` is not present in the firmware.

## Security findings

| # | Severity | Finding |
|---|---|---|
| F1 | High | **Auth-mode downgrade**: vendor RSA signature is optional; short-field VSC path accepts the offline-computable safety code. No vendor private key required to drive 12901. |
| F2 | High (pre-auth) | **Heap overflow in Update**: `E` up to 257 bytes copied to `calloc(0x122)+0x102` → up to 225 bytes past the chunk, reachable with only `Open`+`Update`. Heap grooming/RCE candidate, DoS; no weaponised exploit yet. |
| F3 | Medium | Client-supplied N/E are attacker-controlled; the N copy also overflows the nominal `PKP` layout. No server-side use beyond reply encryption. |
| F4 | Low | `popen()` argument is fixed `"timetest"`; no command injection. If a writable `PATH` directory existed, it could be a root code-exec primitive — see the local analysis report. |
| F5 | Info | Framing checksum and seed obfuscation are not security controls. |

Dynamic proof (qemu-arm-static, private chroot): a short-field client completed
`Open→Update→RS→Check→Run`, `aData` matched, the RSA-verify breakpoint never fired; a
long-field client hit the RSA verify path and failed as expected. `E=257` probes completed
with silent heap corruption.

No vendor private key, certificate or CRT material exists in any extracted firmware tree;
`TelPubBase` contains only the public key.

## Impact for a stock camera

- 12901 can be reached (and started remotely via DVRIP `GetSaftyCode` when `telnetctrl=1`
  and no marker exists) and driven **without the vendor key**.
- It does **not** expose an arbitrary command: `Run` only tries `timetest`, which is
  missing. The exploitable path would be the **pre-auth heap overflow** (RCE research) or a
  `PATH`/file trick if a writable directory is in the daemon's `PATH`.
- Mitigation: keep `/mnt/mtd/Log/9530Disable` at boot, block 12901 at the firewall, and use
  the production image ([production-firmware.md](production-firmware.md)) which starts no
  12901 and no 2323.
- Root on the latest firmware does **not** need 12901: the unsigned V5.07 upgrade path is
  validated in QEMU and on hardware — see
  [upgrade-root-v507.md](upgrade-root-v507.md).

Local analysis (full protocol client, GDB logs, overflow probes):
`stack/analysis/access/rsa-debug/REPORT.md` in the analysis workspace.
